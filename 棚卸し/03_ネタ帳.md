## ① 何が問題だった？

**書きたいネタは日常的に発生するのに、記事になる前に消えていた。そして書き始められなかった。**

SPEC §1・§2 に自分で書いた問題認識から、3層に分けて読み取れる。

### 層1：ネタの取りこぼし
- ネタは移動中・業務中・喋っている最中に出る。しかしPCの前ではない。メモする場所が無いと消える
- ネタと記事は別物。短いネタ（X向け）と、腰を据えた話（note向け）が混在して溜まる

### 層2：着手のハードル
- 「書こう」と思ってから白紙に向かうまでの距離が遠い。SPEC §1の成功指標に **「主指標: 月間公開本数」** を置いた理由が明示されている ──「**時間を最適化しても書き始めなければゼロ**」（付録・維持している判断）
- SPEC §2.4 に問題の核心が書かれている：**「宿題が増えると着手が止まる」**。良かれと思って出す確認事項や修正提案が、そのまま着手を止める要因になる

### 層3：品質のばらつき
- フック・構成・視覚要素・タグ・サムネを毎回その場の頑張りで決めていると、記事ごとに品質が振れる
- そして最も重要な発見 ── **校閲してから「この記事は退屈だ」と気づくのが最も無駄が多い**（SPEC v0.6 中核）。誤字を直す工程と、読む価値があるかを判定する工程は別物なのに、混ざっていた

## ② 現状はどうだった？（着手前の実態）

- ネタの保管：頭の中／散逸
- 執筆：思い立ったときに白紙から
- 品質担保：都度の頑張り
- 公開実績：v0.1体制（`/neta`→`/suikou`→`/kakutei`）で1本目を作成（2026-07-25公開）
- 想定読者は明確だった：**同じ境遇の自治体職員。異動直後・引き継ぎ不足・職場でAI活用に孤軍奮闘している人**

「書くこと自体はできる」が「**続く仕組みが無い**」状態。しかも狙いは単発の記事ではなく、SPEC付録に書かれている通り **3年後にコンサルとして立つための土台づくり**であり、継続が前提の活動だった。

## ③ どう構造化した？

### (a) 入口と出口を物理的に分離した
```
┌─────────────┐      ┌──────────────────┐      ┌──────────────┐
│ スマホ       │      │ PC (Claude Code)  │      │ X / note      │
│ GitHubアプリ │ ───→ │ /memo-to-posts    │ ───→ │ 手直しして投稿 │
│ でIssue起票  │      │ /kaku→/yomu→/kouetsu│    │ →Issueクローズ │
└─────────────┘      └──────────────────┘      └──────────────┘
```
**入口はスマホで30秒、出口はPCでまとめて。** 溜める行為と変換する行為を切り離した。

### (b) Issueをそのまま状態管理に使った（専用ツールを作らなかった）
- 1 Issue = 1ネタ（Xワークフロー）／1 Issue = 1記事（noteワークフロー）
- **オープン＝未投稿、クローズ＝投稿済み**。それ以上の状態管理機構を作っていない
- 優先度は「今すぐ／そのうち／いつか」の3ラベルのみ
- 記事の断片は同じIssueにコメントで追記していく

### (c) 執筆を4つの独立した工程に切った（v0.6の中核）
```
/plan   → (月初・任意) ネタ在庫の棚卸し ＋「3年後の発注者」視点のレビュー
/kaku   → 完成稿を1本書く（選択肢を並べない）＋【要確認】最大3つ
/yomu   → 懐疑派読者2人が質問だけする（最大5問・分類付き）  ★v0.6で追加
/kouetsu→ 校閲差分＋先輩職員ペルソナのレビュー＋タイトル案3つ＋サムネ生成
```
**`/yomu` を `/kaku` と `/kouetsu` の間に挟んだ**のが最大の構造変更。理由も明記されている ──「質問に答えると本文が増えるため、校閲は増えた後にかけないと二度手間になる」。

### (d) 「型」を著者ではなくシステムに持たせた
SPEC §2.5：**「型で担保し、都度の頑張りに依存しない」**。`rules/` 配下に9本の資産を切り出した。

| ファイル | 役割 |
|---|---|
| `kata.md` | 記事の型（最重要）。「庁内をどう通したか」を型に入れている |
| `style.md` | 文体。運用しながら**学習ログを追記**していく |
| `personas.md` | 4種のペルソナ定義（実務担当／AIエンジニア／先輩職員／3年後の発注者） |
| `intake_questions.md` | 素材を引き出す質問リスト |
| `image_style.md` | 本文中画像のスタイル固定文 |
| `checklist.md` / `tags.md` / `hooks_stock.md` / `hyouki.md` | 検品・タグ・フック在庫・表記ゆれ |

付録の一文が構造化の思想を要約している ──「**型は著者が従うものではなく、聞く側が持つもの**」（型に沿って喋ろうとすると自己検閲が入るため、型を質問リストに変えた）。

### (e) 「やらないこと」を仕様書に明記した
SPEC §12 スコープ外、§10.2 に不採用判断の記録。**訂正した判断も残している**（付録）。これは他の4システムには無い、このプロジェクト固有の構造。

## ④ どこを変えた？

### 分担を変えた
| 作業 | 変更前 | 変更後 |
|---|---|---|
| ネタの保管 | 頭の中 | GitHub Issue（スマホから30秒） |
| 素材の整理 | 自分で要約してから書く | **要約しない**。文字起こしをそのまま貼る |
| 第一稿 | 白紙から | `/kaku` が完成稿を1本出す |
| 品質判定 | 自分の主観 | `/yomu` の懐疑派読者2人が質問する |
| 校閲 | 自分で読み返す | `/kouetsu` が差分提案＋ペルソナレビュー |
| 品質の担保 | 都度の頑張り | `rules/` 9本の資産 |
| 画像・サムネ | 都度用意 | `template/thumbnail.html` ＋ `scripts/thumb.py` `chart.py` `shot.py` |

### 途中で自分の判断を訂正した（付録に明記）
これが本システムで最も価値のある部分。**誤りを消さずに残している。**

| 訂正した判断 | 内容 |
|---|---|
| Markdownを使わないと決めたのは誤り（v0.3→v0.6） | noteはMarkdownの一部に対応していた。`■``□`の目印方式は不要な回り道だった |
| 画像生成MCPのROIが低いと判断したのは誤り（v0.4→v0.6） | 価格を確認したら月100円未満。**コストは論点にならなかった** |
| レトロ調の画像スタイルは方向違い（v0.6内で訂正） | 中身が「役所にAIを持ち込む」話なのに絵柄が昭和ではメッセージと逆を向く |

3つとも「**確認せずに下した判断**」が原因で、うち2つは価格や仕様を実際に調べたら覆っている。

### 方針として明確に断ったもの（SPEC §10.2）
**noteへのブラウザ自動投稿を、技術的に可能と確認したうえで不採用にした。** 理由を4点記録している。
1. アカウントリスク（noteに公開APIは無く、自動操作は規約抵触の可能性）
2. 失うものが大きい（3年後の土台を作る活動で、土台自体を賭けることになる）
3. 得るものが小さい（消える手間は**月20分程度**、対して構築数時間＋UI変更のたびに保守）
4. SPEC §2.6「道具作りに時間を溶かさない」と衝突する

代わりに「手作業で3〜5分の工程は自動化しない」という判断基準を明文化し、削る手間を別の方法（表を使わない／画像を1〜2枚に絞る／タグ固定／バッチ運用）で確保した。

## ⑤ なぜAI/ITを使った？

**AIを使った理由 ── 「書く」ではなく「読む側を用意する」ため**

ここが5システムの中で最も特徴的な使い方。AIに文章を書かせること自体は目的ではない。

1. **懐疑的な読者を常時1人用意できる** ── SPEC §5.4の設計原則：**「好意的な読者は記事を強くしない」**。実際の読者に事前に読ませることはできないし、身内は好意的にしか読まない。ペルソナ（30代主任クラス・現実派／AIエンジニア／先輩職員／3年後の発注者）を定義してAIに演じさせることで、**公開前に厳しい質問を受けられる**
2. **ペルソナに文章を直させない** ── これも意図的。「懐疑的な読者は質問しかしてこない」ので、質問に答える形にすると `intake_questions.md` と構造が揃う。AIの役割を「代筆」ではなく「質問」に限定している
3. **第一稿の生成** ── 白紙からの着手ハードルを消す。ただし **`/kaku` は選択肢を並べない**（「何もしなければそのまま公開できる完成稿」を1本出す）。選択肢を出されると選ぶ作業が新しい着手ハードルになるため
4. **要約させない** ── SPEC §2.1：「言い捨てた一言、脱線した愚痴が記事で最も効く素材」。AIが最も得意な要約を、**あえて禁止している**

**AIの暴走を防ぐ制約も同時に設計している**
- §2.2 事実の捏造・誇張は禁止。数字・エピソード・感情を勝手に盛らない。不足は `【要確認: ◯◯】` を**最大3つまで**（うち1枠は費用/時間に固定）
- §2.3 AIが挿入・大幅リライトした箇所に `〔AI挿入〕` `〔AI改〕` の目印を付ける。**無自覚にAIの言葉が混入する状態を作らない**
- §2.7 守秘は自動生成物にも及ぶ。サムネの文書番号は実在の様式に似せつつ架空の記号にする。生成画像に文字を入れさせない

**ITを使った理由**
- **GitHub Issueをそのまま使った** ── スマホの純正アプリがあり、通知があり、状態管理（open/close）とラベルとコメント追記が最初から揃っている。専用アプリを作る理由が無い。SPEC §12で「専用の編集画面（HTML）の自作」を明確にスコープ外にしている
- **noteの下書きをそのまま編集画面として使う** ── 付録の判断：「noteの下書きが既に完成モードそのもの。**道具作りが新しい着手ハードルになるのが最悪の失敗パターン**」
- **Pythonスクリプトは3本だけ**（`chart.py` グラフ／`thumb.py` サムネ／`shot.py` 注釈付きスクショ）。実装は「合計で数時間規模に収める」と宣言している

## ⑥ どういう仕組みにした？

```
【入口】スマホ / GitHubアプリ
   ├ Issueテンプレート memo.yml   → Xネタ（全項目任意・30秒）
   └ Issueテンプレート article.yml → note記事（`記事`ラベル自動付与）
        └ 以降はコメントで断片を追記（音声の文字起こしをそのまま貼る）
                    ↓
【変換】PC / Claude Code のスラッシュコマンド
   /memo-to-posts → posts/YYYY-MM-DD-<Issue番号>.md（X投稿案 140字版＋500字版）
   /plan          → ネタ在庫の棚卸し＋発注者視点レビュー（ファイルは変更しない）
   /kaku <番号>   → articles/YYYYMMDD_スラッグ.md（Markdown完成稿1本）
                    ＋【要確認】最大3つ ＋画像スロット・サムネ・タグ・回遊ブロック
   /yomu <file>   → 懐疑派読者2人の質問 最大5問（致命的/あると良い/記事に不要 で分類）
   〔著者が「致命的」な質問と【要確認】に回答〕
   /kouetsu <file>→ 校閲差分（原文→修正案）＋先輩職員レビュー＋タイトル案3つ＋サムネ再生成
                    ※自動適用はしない
                    ↓
【出口】note の下書きに貼る → 見出し・目次・画像・タグを設定 → 公開（手動）
   → 公開済みラベル付与・Issueクローズ・articles/_published.md 追記（すべて手動）
```

### 設計の要点
- **完全自動化しない境界を引いている** ── `/kouetsu` は自動適用しない、公開は必ず手動、`_published.md` の追記も自動では行わない。AIが最終出力を確定させない構造
- **上限を設けている** ── 【要確認】3つ、`/yomu` の質問5つ。「網羅性より着手可能性を優先する」（§2.4）
- **学習ループを組み込んでいる** ── `style.md` に学習ログを追記していく運用（実際に「初記事から判明した著者の傾向を追記」というコミットがある）。`_published.md` には公開版から判明した運用（タイトルに`【公務員✖️AI】`の冠、タグ5つ）が反映されている
- **バッチ運用を推奨**（§9.2）── 1記事ずつ通すより切り替えコストが小さい

### ここが最大の発見（正直に書きます）
**SPEC §1 の主指標は「月間公開本数 = 月4本（週1本）」。記録上の公開は1本、パイプライン内2本。**

一方で**仕様書は16日間で6版まで進化している**。つまり ──

> **道具の進化速度が、記事の産出速度を上回っている。**

これは SPEC §2.6「**道具作りに時間を溶かさない**」および付録「道具作りが新しい着手ハードルになるのが最悪の失敗パターン」という、**自分で書いた原則に抵触している可能性がある**。しかも本人がその失敗パターンを最も明確に言語化しているシステムで起きている点が重要。

ただし擁護材料もある：v0.6で追加した `/yomu` は「校閲してから退屈だと気づく無駄」を消す工程で、質に直接効く。ブラウザ自動投稿は正しく却下している。**「作りすぎ」ではなく「作る対象の選び方は正しかったが、回す前に版を重ねた」**という読み方もできる。

### さらに ── 8/3以降、約4週間コミットが止まっている
最終コミットは 2026-08-03「改行コードをLFに固定」。今日（8/30）まで動きが無い。同時期に献立アプリは8/27・8/28に更新されている。**引っ越し（Mac移行）を境に、このシステムだけ再開していない**可能性がある。

## ⑧ 次に何を改善できる？

### A. 最優先：道具を止めて、回す（優先度：最高）
1. **v0.7に手を付ける前に、v0.6のまま記事を3本通す** ── SPEC §13の将来拡張リストには7項目あるが、**着手すべきではない**。v0.6の `/kaku`→`/yomu`→`/kouetsu` は一度も複数記事で回っていない。回す前に改善案を実装すると、⑦で指摘した構造が繰り返される。判断基準は自分で書いてある：「成功指標を本数にした ── 時間を最適化しても書き始めなければゼロ」
2. **止まっている2本を先に出す** ── `articles/` に校閲済み1本・公開待ち1本がある。**新しいネタより先にこれを公開する**。在庫があるのに止まっているのは、道具の問題ではない
3. **止まった理由を特定する** ── 8/3以降の停止が (a) 引っ越しで環境が無かった (b) 忙しかった (c) `/yomu` の質問に答えるのが重かった のどれかで、打つ手が全く違う。(c) なら §2.4 の上限（5問）をさらに絞る必要がある

### B. 学習ループが閉じていない（優先度：高）
4. **`_published.md` の「反応(スキ数など)」が (未記録) のまま** ── SPEC §13の将来拡張の**第1位が「反応データを学習ループに繋ぐ（最優先）」**。しかし1本目の反応すら記録されていない。スキ数を1つ書き込むだけなら5分。**これをやらないと `style.md` `kata.md` の改善が主観のままになる**
5. **`style.md` の学習ログ運用が1回で止まっている** ── 7/23に初記事から追記した以降、更新が無い。記事を出すたびに1行追記する運用に戻す

### C. 仕組みの穴（優先度：中）
6. **ペルソナが実読者に基づいていない** ── §13の7番目に「ペルソナを増やす ── 反応を見て、実際に読んでいる層に合わせて調整」とあるが、反応データが無いので調整できない。(4)と依存関係にある
7. **Xワークフローがほぼ動いていない** ── `posts/` に1本のみ。noteワークフローに比べて明らかに使われていない。**「Xは別システムとして畳む」判断もあり得る**。1リポジトリに2ワークフローを載せている構成自体を見直す価値がある
8. **`/plan` が使われた形跡が無い** ── 月初運用の想定だが、実行ログもコミットも無い。月次の棚卸しが回っていないなら、Routine（定期実行）に載せるか、諦めて仕様から外す

### D. 資産としての価値（優先度：中）
9. **SPEC付録「判断の履歴」自体が記事になる** ── 「訂正した判断」3件（Markdown・画像生成MCP・レトロ調）は、**確認せずに判断して覆った実例**として、想定読者（自治体職員）に最も刺さる型。しかも `kata.md` の「庁内をどう通したか」とは別軸の、AI活用の実務知として価値がある。在庫として `/plan` に入れておく

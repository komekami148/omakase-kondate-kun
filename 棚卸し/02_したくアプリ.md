## ① 何が問題だった？

**3歳の子ども（自閉症・ADHD）が、朝の身支度に取りかかれない・続かない。**

READMEの記述から読み取れる問題設定は明確で、対象が特性のある子どもであること自体が設計条件になっている。

- 「次に何をするか」が本人の頭の中にないと動けない。口頭の指示は流れて消える
- 指示を出す側（親）が毎回全項目を言い続けることになる。朝の忙しい時間帯にこれが毎日発生する
- 一般的な「やることリスト」は、文字が読めない・チェックの意味が分からない3歳には使えない
- ADHDの特性上、**取りかかり（開始）そのものにエネルギーが要る**。「やることが分かっている」だけでは足りず、やる気の後押しが要る

問題は「タスク管理ができていない」ことではなく、**開始の動機づけと、進捗の可視化を、親の声かけが全部背負っていた**こと。

## ② 現状はどうだった？（着手前の実態）

- 身支度の手順：親が口頭で毎回指示
- 進捗の把握：親の記憶（どこまで終わったか）
- 動機づけ：親の声かけとテンションに依存
- 記録：なし
- 市販の支援グッズ（絵カード等）：紙で運用すると、状態のリセットや持ち運びの手間が発生する

つまり**親の稼働がボトルネック**で、しかも朝という最も余裕のない時間帯に集中していた。

## ③ どう構造化した？

### (a) 「やる」→「できた」の2段階に分解した
これが設計の中心。1タップの完了チェックではなく、**開始の宣言（やる）と完了の申告（できた）を分けている**。

- ADHDの特性で難しいのは「終わらせること」より「始めること」。開始を1つのアクションとして独立させ、そこに報酬（効果音）を置いた
- 途中の状態（＝やると宣言したが終わっていない）が画面に残るので、親も子も今どこにいるか一目で分かる

### (b) 3歳が単独で操作できる形に制約を絞った
- **絵文字＋ひらがな**の大きなボタン（文字が読めなくても絵で判別できる）
- 操作は「押す」だけ。ドラッグ・長押し・スワイプなし

### (c) 報酬を段階的に重ねた
効果音（やる／できた）→ お祝い演出 → BGM（おしたくミュージック）と、コミット履歴上で報酬レイヤーを足していっている。

### (d) データは1端末・1キーに閉じた
`localStorage` の `shitaku-v1` キーに、項目・チェック状態・音量・音の好みをまとめて保存。**サーバーに何も送らない**（README明記）。子どもの生活記録という性質上、外に出さない設計を選んでいる。

## ④ どこを変えた？

### 分担を変えた
- 手順の提示：**親の口頭 → 画面**
- 進捗の把握：**親の記憶 → 画面の状態**
- 動機づけ：**親の声かけ → 効果音・お祝い演出・BGM**（親のテンションに依存しなくなる）

### コミット履歴に残る「作り直しの密度」
音まわりを**2日間（7/6〜7/8）で4回作り直している**。

| 07-08 | おしたくミュージックを応援歌ふうのブラス+太鼓アレンジに強化 |

読み取れること：
- **「効果音を選べるように」した時点で、子どもの反応に個体差・日差があると分かっている**。固定の正解を作るのではなく、選択肢を用意する方向に振った
- 「やさしい → おまつり」への差し替え、「応援歌ふうのブラス+太鼓」への強化、「踊りたくなる3曲」── **より刺激の強い方向へ一貫して寄せている**。実際の反応を見て、盛り上がる方が効くと判断したことがうかがえる
- 「画面ロック復帰後に音が鳴らない」「お祝い画面がタッチで消えない」は、**実機で毎朝使っていないと絶対に出てこないバグ**。日常運用に乗っている証拠

Mac移行を機に `index.html` へ一本化し（重複ファイルを削除）、READMEを新規追加。**「新しいマシンで開発を再開する場合（例: Mac）」の手順まで書いている**── 環境が変わっても再開できる形に、自分向けの引き継ぎ資料を残した。

## ⑤ なぜAI/ITを使った？

**このシステムは、実行時にAIを使っていない。** そこが他の4つと決定的に違う。

- 献立アプリと違い、身支度の手順は**毎日同じ**。生成する必要がない。ここでAIを使うのは過剰
- 代わりにITで解いたのは「**状態の保持**」と「**報酬の即時提供**」の2点

**ITを使った理由**
1. **状態を持てる** ── 紙の絵カードだと、毎朝リセットする手間が親に戻ってくる。localStorageに持てば日付が変われば自動でリセットされる
2. **音を出せる** ── 紙ではできない。即時のフィードバック（押した瞬間に音が鳴る）は、開始の動機づけとして紙より強い
3. **調整が即座にできる** ── 反応が悪ければその日のうちに音を差し替えられる（実際に2日で4回やっている）。既製品では不可能

**AI（Claude Code）を使ったのは「作る側」** ── 音源ファイルを用意せず、Web Audio APIでブラス・太鼓・メロディを合成するコードを書く、というのは通常なら手が出ない領域。ここは開発側でAIを使っている。

**技術選択の合理性**
- **音声ファイルを一切持たず、Web Audio APIで実行時生成** ── リポジトリが軽い、読み込みが速い、著作権の問題が発生しない、曲の差し替えがコード修正だけで済む（実際に4回差し替えている）
- **単一HTML＋GitHub Pages** ── サーバー費用ゼロ。pushすれば数十秒で子どものタブレットに反映される。この「即反映」が、上のチューニング速度を支えている
- **外部ライブラリなし** ── 依存の更新に振り回されない

## ⑥ どういう仕組みにした？

```
[ 単一 index.html ]（GitHub Pages が master 直下をそのまま配信）
   ├ 項目リスト        … 絵文字＋ひらがなの大ボタン
   ├ 2段階の状態遷移   … 未着手 →(やる)→ 実行中 →(できた)→ 完了
   ├ 効果音エンジン    … Web Audio API で実行時合成（GO_SOUNDS / DONE_SOUNDS から選択）
   ├ おしたくミュージック … MUSIC_TRACKS（おまつり／ソーラン／フォークダンス／ジェンカ 等）
   ├ お祝い演出        … 全項目完了時
   └ 設定画面          … 項目の編集、音の好み、音量
                          ↓
                    localStorage['shitaku-v1']
                    （項目・チェック状態・音量・音の好み。外部送信なし）
```

**運用サイクルが極端に短い**
```
子どもの反応を見る → index.html を直接編集 → commit & push → 数十秒でPagesに反映 → 翌朝試す
```
ビルドなし・ファイル1つ・依存なし、という制約が、この日次チューニングを可能にしている。**「作り込まない」ことが機能している**例。

## ⑦ 何が変わった？

### 記録から確認できること
- **公開URLで動く道具になった**（GitHub Pages）。端末を選ばず、URLだけで子どものタブレットでも親のスマホでも開ける
- **親の口頭指示という単一障害点が、画面に置き換わった**（少なくとも仕組みとしては）
- **反応を見て即日直せる体制ができた**。7/6〜7/8の3日間で6回改修している
- **約7週間の空白（7/10頃 → 8/25）を経て戻ってきている**。8/25の変更が「Mac移行の整理」と「お祝い画面のバグ修正」であることから、**空白期間も使い続けていた**（使っていなければバグに気づかない）と読める
- **記録機能を意図的に持っていない** ── できた回数の履歴やグラフは実装されていない。「その場の後押し」に機能を絞っている

### 【要確認】実際の効果
- 朝の身支度にかかる時間・親の声かけ回数の変化
- 子どもが一人で最後まで通せるか、どの項目で止まるか
- どの曲・どの効果音が実際に効いているか（＝選択肢のうち何が使われているか）

## ⑧ 次に何を改善できる？

### A. 使われ方が見えていない（優先度：高）
1. **記録が一切残らない** ── できた回数も、どこで止まったかも、どの曲を選んだかも保存していない。**⑦の【要確認】が埋められないのは、この機能が無いから**。ただし「記録を見せる」機能を子ども向け画面に足すと複雑になるので、**親だけが見える簡易ログ**（日付ごとの完了項目を localStorage に追記し、設定画面の奥で一覧表示）に留めるのが筋。これが入ると「効いているか」を初めて事実で語れる
2. **どの音が選ばれているかが分からない** ── 選択肢を4回作り直したのに、どれが当たりだったかのデータが無い。上のログに含めれば済む

### B. 運用上のリスク（優先度：中）
3. **PWA対応していない**（`manifest` 無しを確認）── 献立アプリはPWA対応しているのに、こちらは未対応。ホーム画面から全画面で起動できない、オフラインで開けない。**朝、電波が悪い/機内モードのときに使えない**のは実用上の穴。単一HTMLのままでも `manifest` の内包とService Workerの追加は可能で、献立アプリに前例がある
4. **データが1端末のlocalStorageのみで、バックアップ手段が無い** ── 献立アプリにはJSONのエクスポート/インポートがあるが、こちらには無い。項目を作り込んでいる場合、ブラウザのデータ削除で消える。端末を変えるときも作り直しになる

### C. 拡張の候補（優先度：中〜低）
5. **場面ごとのリスト切り替え** ── 現在は1つのリスト。「朝の支度／帰宅後／寝る前」を切り替えられると、同じ仕組みが1日3回使える。項目セットを複数持てるようにするだけで済む
6. **下の子（1歳）への展開** ── 献立アプリの仕様書から家族構成が分かる。将来的に2人分を管理するなら、上の(5)と同じ「プロファイル切り替え」の構造で吸収できる
7. **絵文字ではなく写真を使えるように** ── 自閉症の支援で使われる絵カードは「その子の実物の写真」が効くことがある。localStorageに画像を持つと容量が厳しいので、採用するなら要検討
8. **感覚過敏への配慮の明示** ── 音を強くする方向に一貫して寄せてきたが、日によって刺激が強すぎる場合に備え、「音なしモード」がワンタップで切れると安全。設定の奥ではなく表に出す価値がある

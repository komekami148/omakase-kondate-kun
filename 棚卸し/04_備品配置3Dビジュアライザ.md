## ① 何が問題だった？

**施設の備品配置と備品予算の積算が、Excelの表と平面図の往復でしか検討できなかった。**

デモ版の機能構成（予算モード・積算表・流用による抑制額・金額ヒートマップ）から、解いていた問題は「3Dで見たかった」ではなく **「配置の妥当性と、金額の妥当性を、同じ画面で判断したかった」** と読める。

推定される問題は3つ。

### (a) 配置が想像できない
- 数十室ある居室、食堂、浴室・脱衣室、リネン室、汚物処理室、談話コーナー…という規模の施設で、「この部屋にこの備品が本当に収まるか」を平面図の寸法から頭の中で立体に起こす必要があった
- 関係者（施設担当者・現場職員・上層部）に説明するとき、図面が読める人と読めない人で理解の差が出る

### (b) 配置と金額が別の資料に分かれている
- 配置は図面、金額はExcelの積算表。**片方を直すともう片方と合わなくなる**
- 「この備品を減らしたら、いくら減るのか」が即座に出ない。査定・調整のたびに手作業で再集計

### (c) 現施設からの流用が計算に乗りにくい
- データに「現施設居室」「現施設食堂」という部屋が存在し、UIに「**流用による抑制額（参考）**」「**合計（新規購入）**」という区別がある
- つまり**既存備品をどれだけ持っていくかで新規購入額が変わる**。この「流用したらいくら浮くか」を手計算で回すのは、備品の点数を考えると現実的でない

## ② 現状はどうだった？（着手前の実態）

- 配置検討：平面図（紙・PDF）＋想像
- 積算：Excelの品目別集計表
- 流用の反映：手作業で品目ごとに差し引き
- 関係者への説明：図面と表を並べて口頭で補足
- 変更が入ったとき：図面と表の両方を直す（＝二重管理）

## ③ どう構造化した？

### (a) 「部屋」と「備品」を分離し、両者をマスタで結んだ
`index.html` 内のデータモデルを実測した結果、5つのトップレベル構造を持っている。

```
{
  roomCategories : [ 居室 / 食堂 / 浴室 / バックヤード / 廊下 / 中庭 … ]（色を持つ）
  itemCategories : [ ベッド / 家具 / 家電 ]（色を持つ）
  itemTypes      : [ { label, category, size:[W,D,H], unitPrice } … ]
  floors         : [ 1F / 2F / 3F / 屋上 … ]
  rooms          : [ 各部屋と、そこに置かれた備品の配置 … ]
}
```

**設計の要点は `itemTypes` が「寸法」と「単価」を同時に持っていること。** これが構造化の中核で、以下が同じデータから導出できるようになる。

| 欲しいもの | 導出元 |
|---|---|
| 3Dの見た目 | `size` |
| 部屋に収まるか | `size` × 部屋の座標 |
| 積算表（品目別・部屋別） | `unitPrice` × 個数 |
| 金額ヒートマップ | `unitPrice` の部屋別合計 |
| 流用による抑制額 | 「現施設」由来の備品を新規購入から除外 |

**配置を直せば金額が自動で変わる。** ②の二重管理はここで解消されている。

### (b) 用途ごとに3つのモードに分けた
- **閲覧モード** … 見る・説明する（部屋クリックで詳細）
- **予算モード** … 積算表・金額ヒートマップ・CSV出力
- **編集モード** … 備品をドラッグで移動、Rキーで90度回転、Ctrl+Zで取り消し、5cmグリッドスナップ

同じデータに対して、**見る人・積む人・動かす人の3つの視点を用意した**。

### (c) 説明のためのカメラプリセットを用意した
「全景」「各階真上」「各階斜め45°」「ウォークスルー」の4つ。特に **各階真上＝従来の平面図**、**ウォークスルー＝現場の目線**。図面が読める人にも読めない人にも同じデータで説明できる。

### (d) 「対象外にする」を機能として持たせた
備品を削るのではなく**対象外にマークする**（15箇所で参照）。査定で落とされた項目を消さずに残せる ── 復活する可能性がある予算検討の実務に合っている。

## ⑤ なぜAI/ITを使った？

**このシステムも、実行時にAIを使っていない。** Three.jsによる3D描画と、素直な集計処理だけ。

**ITで解いた理由 ── 3つの表現を1つのデータから出したかったから**

- 3D表示・平面図・積算表は、本来なら3つの別ツール（CAD／図面／Excel）で作るもの。それぞれが独立していると**更新のたびに3箇所を直すことになり、必ずズレる**
- `itemTypes` に `size` と `unitPrice` を同居させた1つのJSONから全部を導出することで、**ズレる余地を構造的に消した**。これがITを使う本質的な理由
- 「配置を1つ動かしたら金額がどう変わるか」を**その場で答えられる**状態は、査定・調整の場で効く。Excelの再集計では会議中に間に合わない

**AI（Claude Code）を使ったのは「作る側」** ── Three.jsでの3Dシーン構築、カメラプリセット、ウォークスルー、グリッドスナップ、Ctrl+Z（undoスタック）といった実装は、通常なら専門の開発工数がかかる。ここを開発側のAIで吸収している。**5日間でPhase 2Cまで到達している速度**が、それを裏づけている。

**単一HTMLを選んだ理由（他の4システムと共通）**
- インストール不要。**ファイルを1つ渡せば誰の端末でも開く**。庁内で共有する道具として、これは決定的に重要（インストール申請や環境構築が要るツールは配れない）
- サーバー不要 ＝ セキュリティ審査や運用費の議論が発生しない
- Three.jsを外部CDNではなく同梱している（765KB）ため、**オフラインでも動く**。閉じたネットワークでも使える

## ⑥ どういう仕組みにした？

```
[ 外部JSON ]（施設データ：部屋・備品・単価・階）
      │  「データ読込」ボタン → FileReader
      ▼
[ 単一 index.html（Three.js 同梱・765KB） ]
      │
      ├ validateData()  … トップレベル5キーの検証
      │                   （roomCategories / itemCategories / itemTypes / floors / rooms）
      │
      ├─ 閲覧モード … 部屋クリックで詳細、部屋名・備品名で検索
      │              壁の高さ切替（腰高／全高）※俯瞰と没入の使い分け
      │              カメラ：全景／各階真上／各階斜め45°／ウォークスルー
      │
      ├─ 予算モード … 積算表（品目別・全館／部屋別）
      │              合計（新規購入）／流用による抑制額（参考）
      │              金額ヒートマップ ○/● 、新規のみ表示、単価未登録の明示
      │              CSV出力
      │
      └─ 編集モード … ドラッグ移動／Rキーで90°回転／5cmグリッドスナップ
                     Ctrl+Zで取り消し／対象外にする／「未保存の変更があります」警告
      ▼
[ 出力 ] CSV（積算表）／ PNG（画面キャプチャ）／ 保存（JSON）
```

### 実装上の判断で目を引くところ
- **ブラウザに何も保存していない**（`localStorage` 不使用を確認）。状態はすべて読み込んだJSONと画面上のみ。その代わり **「未保存の変更があります」の警告**を出している。データの正本をファイル側に置く設計 ── 業務データを扱う道具として、ブラウザに残さないのは妥当
- **「単価未登録」を隠さず表示する** ── 積算の抜けを黙って0円で通さない。査定に出す資料を作る道具として重要な配慮
- **壁の高さを切り替えられる**（腰高／全高）── 腰高＝上から中が見える（検討用）、全高＝実際の見え方（説明用）。同じシーンを2つの目的で使い分けている

## ⑧ 次に何を改善できる？

### A. 前提の確認が先（優先度：最高）
1. **実データ版が今どうなっているかを確認する** ── デモは7/21で止まっている。実データ版が(a)完成して使い終わった (b)途中で止まった (c)そもそもデモ止まり のどれかで、以下すべての優先度が変わる。**5システム中、唯一「本体が手元にあるか分からない」もの**
2. **実データ版がローカルにしか無いなら、退避する** ── 献立アプリ・したくアプリ・ネタ帳はすべてGitHubにあるが、これだけデモしか無い。Mac移行を経ているので、**前のPCに置き去りになっていないか**を最優先で確認する（private リポジトリにするか、少なくともバックアップを取る）

### B. 道具として足りていないもの（優先度：高）
3. **データを作る手段が無い** ── 読み込みはあるが、部屋や備品マスタを一から作る画面は無い。JSONを手で書くか別途用意する必要がある。**次の施設で使い回すときに、ここが一番の障壁になる**。最低限、CSV（Excel）からJSONを生成する変換スクリプト1本があれば再利用性が跳ね上がる
4. **単価マスタの更新経路が無い** ── 単価はJSON内に直書き。年度が変われば単価は変わる。積算ツールとして繰り返し使うなら、単価だけ別ファイルに分けて差し替えられる形にしたい
5. **「未保存の変更があります」で守っているだけ** ── 編集モードで作業中にブラウザが落ちると失う。localStorageに一時退避を入れるか、自動でJSONを吐く仕組みがあると安心（業務データをブラウザに残さない方針とは衝突するので、**明示的な一時保存ボタン**が落としどころ）

### C. 説明力の強化（優先度：中）
6. **積算表のPDF/印刷対応** ── CSVとPNGは出せるが、決裁や査定に出す形（表として印刷できるA4）が無い。CSVをExcelで整形する手間が残っているはず
7. **配置案の比較（A案/B案）** ── 査定や協議では「減らした場合」を並べて見せる場面があるはず。対象外マークの状態をセットで保存・切替できると、そのまま比較資料になる
8. **Phase 2Cの続き（Phase 3？）が未定義** ── 献立アプリやネタ帳と違い、**このシステムだけ仕様書が無い**。何をどこまで作るつもりだったかが本人の頭の中にしかない。再開するなら、まず1ページの仕様メモを書く

### D. 資産としての活用（優先度：中）
9. **デモ版がそのまま発信素材になる** ── 架空データで動く公開URLがあるのは強い。ネタ帳の想定読者（自治体職員）に対して「3Dで積算した話」は、`kata.md` の「庁内をどう通したか」の型にそのまま乗る。**記事在庫としてIssue化する価値がある**（→ 03_ネタ帳.md ⑧-9 と同趣旨）
10. **GitHub Pagesで公開していない** ── したくアプリはPagesで公開しているのに、こちらはリポジトリにHTMLがあるだけ。Pages設定を有効にすればURLで見せられる。**(9)をやるなら必須**

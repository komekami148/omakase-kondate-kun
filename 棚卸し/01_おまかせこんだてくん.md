## ① 何が問題だった？

**毎週の献立決めで、同じ前提条件を毎回ゼロから入力し直していた。**

仕様書 §1 に自分で書いた背景がそのまま問題定義になっている。

- Geminiのチャットで毎週献立を相談していたが、**家族構成・食材バランス・重複回避・こだわり条件といった「定型部分」を毎回手入力**していた
- 定型部分の再入力は、献立を考える本質的な作業ではない。にもかかわらず毎週発生する
- さらに「先週と被らないようにする」は人間が覚えていないと機能しない。チャットは前回の会話を持っていないので、**重複回避が毎回ユーザーの記憶頼み**だった
- 大人2人＋3歳・1歳という家族構成上、「子どもが食べやすい」「取り分け対応」の条件も毎回書く必要があった

問題の本質は「AIが献立を考えられないこと」ではなく、**AIに考えさせるための前提を、人間が毎回運んでいたこと**。

## ② 現状はどうだった？（着手前の実態）

- 献立相談：Geminiチャットに毎回手入力（定型条件の再入力あり）
- 重複回避：本人の記憶
- 買い物リスト：チャットの回答から自分で拾って作成
- 家族への共有：口頭またはその都度LINEに手打ち
- 過去に何を作ったかの記録：なし（＝好みの傾向も蓄積されない）

つまり「提案」だけがAI化されていて、**その前後（条件入力・買い物リスト化・共有・記録）が全部手作業**という、部分最適の状態。

## ③ どう構造化した？

### (a) 工程を1本の線につないだ
バラバラだった作業を、明示的な一連のフローとして定義した。

```
条件選択 → AI提案 → 採用 → 日付割り当て → 買い物リスト → LINE共有 → 星評価
```

### (b) Phase 1〜4 に分割して、やらないことを先に決めた

| Phase | 内容 | 状態 |
|---|---|---|
| 1 | 条件選択→提案→採用→買い物リスト→LINE共有 | 完了（2026-07-12） |
| 2 | 献立カレンダー・星評価・料理ライブラリ | 完了（2026-07-12） |
| 3 | 評価の提案反映、買い忘れレスキュー、調理中相談チャット | **未着手** |
| 4 | Firebase(Firestore)による家族リアルタイム共有 | 未着手（必要なら） |

Phase 1仕様書 §8 に「Phase 1のスコープ外（やらないこと）」を明記し、副菜・汁物・カレンダー・評価反映を**意図的に外した**。スコープを閉じることで初版を完成させている。

### (c) 「3つのキモ」を設計原則として抽出し、判断基準にした
仕様書 §10 で、やり取りログから3原則を抽出し、各機能をそこに紐づけている。Phase 2以降の機能追加もこの基準で判断する、と宣言している。

| キモ | 実装での対応 |
|---|---|
| 共感と労いのテキスト | UIテキスト方針（ローディング・エラー文言含む）＋ AI応答の `greeting` フィールド |
| リカバリー（ボタン一つで修正） | 「これは変えて」ボタン（一言理由つきで、そのカードだけ再生成） |
| 文脈の記憶 | 直近14日の採用メニュー名を毎回プロンプトへ自動挿入 |

### (d) データを「後で差し替えられる形」に切った
localStorageの読み書きを `StorageService` に一本化。Phase 4でFirestoreに差し替えられるようにした（実装確認済み：`StorageService` / `GeminiService` / `ShoppingList` の3モジュールが `index.html` 内に存在）。

## ④ どこを変えた？

### 作業の分担を変えた
- 定型条件の保持：**人間 → アプリ**（家族プロフィール・タンパク質マスタ・こだわりタグ・常備品リストを設定に持たせた）
- 重複回避：**人間の記憶 → 自動**（直近14日の採用メニューをプロンプトに自動挿入）
- 買い物リスト作成：**人間 → 自動**（材料を合算し、常備品を分離し、野菜→肉魚→その他の順に並べる）
- 過去の記録：**なし → 蓄積**（`adoptedHistory` に採用日・予定日・星・メモを保存）

### 実装方針を途中で変えた（コミット履歴に残っている判断）
| 日付 | 変更 | 意味 |
|---|---|---|
| 07-16 | 献立生成を**Google検索グラウンディング → スキーマ検証方式**に変更 | 出力の安定性を優先。検索の付加価値より、JSONが毎回正しく返ることを取った |
| 07-17 | 503（サーバー混雑）にも自動リトライを適用 | 家庭で使う道具として「たまに失敗する」を許容しない |
| 07-17 | タイムアウトを追加し、**再試行を1回に簡略化** | 粘るより早く諦めて再操作させる方が体感が良い、という判断 |
| 07-17 | デフォルトモデルを `gemini-flash-lite-latest` に変更 | コストと速度を優先 |

### 運用してから直したところ（実使用のフィードバック）
- 07-21 カレンダーを**月曜始まり**に変更／買い物リストのチェック済みを除外・永続化
- 07-30 買い物リストのコピー時にチェック済み商品が復活する不具合を修正
- 08-03 バックアップ機能の抜けを修正（Mac移行のタイミング）
- 08-27 **定番メニューをカレンダーに直接入力**できるように＋**お昼ごはん欄**を追加
- 08-28 カレンダーのマス目を画面下まで広げ、レシピ名が途切れないよう調整

08-27の変更は設計思想の修正として重要：**「毎回AIに考えさせる」前提だったものに、「決まってるものは決まってると打てばいい」経路を足した**。AI必須のフローから、AIを使わない近道を用意する方向へ動いている。

## ⑤ なぜAI/ITを使った？

**AI（Gemini API）を使った理由 ── 献立提案は「正解が無数にあり、条件の組み合わせが毎回違う」から**

- 「鶏むね2回・豚こま1回、15分以内、子どもが取り分けできる、ナスとオクラを使い切りたい、先週の6品とは被らない」── この条件の掛け合わせをルールベースで書くのは非現実的。レシピDBを持って検索する方式でも、条件の組み合わせが毎回変わるので当たらない
- 「子どもが食べやすい取り分け方」のような、**レシピに書かれていない補足（`kid_note`）を生成できる**のは生成AIの固有の強み
- 一方で、**AIに任せない部分は明確に切り分けている**：材料の合算・常備品の分離・カテゴリ並べ替えは `ShoppingList` の純粋関数として実装（AIに計算させると間違えるうえ検証できないため）。AIには「JSONを返させる」だけにして、加工は自前コードでやる、という分担

**ITで作った理由 ── チャットのままでは状態を持てないから**

- 履歴・設定・評価という**状態**が必要だった。チャットは状態を持たない
- 家族に渡すには「画面」が要る。買い物リストのチェック消し込みは、スマホの画面で指で触る操作でしかできない

**単一HTML＋localStorageを選んだ理由（仕様書 §3, §11.2）**
- フレームワーク・ビルドツールを禁止（React/Vue/Vite/npm 不使用）、ファイルは1つのまま
- サーバーもアカウントも不要 → 運用コストゼロ、家族に配るのが URL 一つで済む
- APIキーはコードに埋め込まず、設定画面から入力して localStorage に保存

## ⑥ どういう仕組みにした？

### 全体構成
```
[ 単一 index.html（PWA） ]
   ├ StorageService  … localStorage の唯一の窓口（→将来Firestoreに差し替え可能）
   ├ GeminiService   … プロンプト生成 / API呼び出し / JSONスキーマ検証 / リトライ
   ├ ShoppingList    … 材料の合算・常備品分離・並べ替え（UI非依存の純粋関数）
   └ UI              … 5タブ（ホーム / カレンダー / ライブラリ / 買い物リスト / 設定）
```

### AI連携の型
毎回アプリが自動でプロンプトを組み立てる。
- 固定部：役割（家庭料理の献立アドバイザー、冒頭に労いを添える）＋ 家族プロフィール ＋ JSON厳守指示
- 可変部：提案数（指定回数**+2品**＝選択の余地を持たせる）、タンパク質割り当て、こだわりタグ、自由記入、**直近14日の採用メニュー名**、現在の月（旬の判断材料）
- 出力は固定スキーマのJSON（`greeting` / `menus[]`。各メニューに `name` `description` `protein` `cooking_time_min` `kid_note` `ingredients[]` `steps[]`）
- `ingredients` は `amount`（数値）と `unit`（単位）を分離。**買い物リストで合算するため**の設計判断
- `category` は `野菜 | 肉魚 | その他` の3値に限定 → 並べ替えを機械的に処理できる

### 失敗の受け止め方を設計に入れている
- JSONパース失敗 → 自動リトライ1回 → それでも失敗なら「もう一度」ボタン
- 通信エラー → **責めないトーン**のトースト（「うまく受け取れませんでした。もう一度だけ試させてください」）
- APIキー未設定 → 設定画面へ誘導
- デモモード（モックJSON）を設定画面に残し、**APIキーなしで家族にデモできる**ようにした

### 作り方そのものを構造化した（仕様書 §11）
Claude Codeに実装させる前提で、Step 1〜7の実装順と**各ステップの動作確認方法**を仕様書に書いた。特に Step 4 で「まずモックAIで画面を完成させ、Step 6で実APIに差し替える」としている。禁止事項（フレームワーク不可・ファイル分割不可・仕様外の機能追加不可・モデルIDを記憶で推測しない）も明文化。

## ⑦ 何が変わった？

### 記録から確認できること
- **1本の道具に統合された**：条件選択からLINE共有・星評価まで、アプリ内で完結する（Phase1・Phase2の受け入れ条件を各7項目・6項目で定義し、達成扱いでコミットしている）
- **重複回避が人間の記憶から外れた**：直近14日の自動挿入により、覚えておく必要がなくなった
- **記録が貯まる状態になった**：星評価＋一言メモが `adoptedHistory` に蓄積。これはPhase 3の入力データになる設計
- **2か月間、使いながら直し続けている**：7/12完成 → 8/28まで改修が続いている。しかもバグ修正（チェック復活・バックアップ抜け）や体験改善（月曜始まり・マス目の高さ）といった、**実際に使わないと出てこない指摘**が並んでいる。＝作って終わりではなく運用に乗った
- **AIを使わない経路が追加された**：定番メニュー直接入力・お昼ごはん欄（8/27）。実運用の中で「毎回AIに聞くほどでもない日」の存在が見つかった

## ⑧ 次に何を改善できる？

### A. すでに自分で設計済みで、着手していないもの（優先度：高）
1. **Phase 3：評価の提案反映** ── 仕様書に引き継ぎメモまで書いてある。★4以上は「好みの傾向」として要約してプロンプトへ、★2以下は回避リストへ、`ratingMemo` はそのまま素材に使う。Phase 2仕様書に「評価データが2〜3週間分たまってから着手するのが望ましい」と書いており、**7月から運用しているので条件は既に満たしている**。ここが最大の未回収
2. **Phase 3：買い忘れレスキューモード／調理中相談チャット**（「辛すぎた」等）── 「3つのキモ」の1つ「リカバリー機能」は提案段階（これは変えて）しか実装されておらず、調理中は未対応のまま
3. **Phase 4：Firestore同期** ── `StorageService` を作った目的そのもの。家族が各自の端末で買い物リストを見る運用になるなら効いてくる

### B. 設計上のリスク（優先度：中）
4. **データがlocalStorageのみ＝端末依存** ── バックアップ（JSONエクスポート/インポート）は実装済みだが、**手動**。8/3に「バックアップ機能の抜け」を修正した経緯もあり、ブラウザのデータ削除で全履歴が消えるリスクは残っている。定期リマインドか、Phase 4の前倒しを検討する価値がある
5. **`ShoppingList` の検証が手動** ── 「UIから独立した純粋関数群として実装（単体で検証しやすくする）」と設計したのに、テストが無い。合算ロジックのバグ（1個+1/2個→1.5個、単位違いの併記）は買い物の場で初めて気づくタイプ。単一HTMLの方針を崩さずに、簡易テスト用の隠しページを1つ足せば回帰確認が効く

### C. 運用で見えてきたこと（優先度：中〜低）
6. **副菜・汁物がスコープ外のまま** ── Phase 1で意図的に外したが、実運用が2か月続いた今、必要かどうかを判断できる材料が揃っているはず。要否を再判定する
7. **「定番メニュー」の資産化** ── 8/27に直接入力を足したが、これは実質「AIを介さない献立ソース」。ライブラリの「もう一度作る」と役割が重なっている可能性がある。統合するか、役割を明確に分けるか
8. **モデル選定の見直し** ── `gemini-flash-lite-latest` を7/17に選んで以降そのまま。仕様書自体が「モデルIDを記憶から推測せず公式ドキュメントで確認する」と定めているので、定期的な確認を運用に組み込む
